# 人物坐标消失追踪 · 2026-10-19

已复现的主要原因是 **前端把「5 秒没有新坐标」当成人物过期删除，而协议是按变化发送移动字段**。静止人物可以长时间没有位置字段，期间仍有视角/状态更新，之后的坐标与之前相同。上一轮 5 秒暂存只缓解短暂坏样本与请求失败，没有解决这种生命周期差异。

本轮是日志与源码定位，没有调整生产解析器、延长超时或修改采集网络配置。

## 源码链路

1. `native/src/ue_movement.cpp`：只有 `mask & 1` 才读取 `pos/pv/rot`；`mask & 32` 是 `u160` 视角。因此一个人物在包中出现不代表本次一定发送位置。
2. `native/src/players.cpp` 的 `position()`：没有 `pos` 时不产生 `player_sample`；完整帧包含视角则产生独立 `player_motion`。这能避免把视角更新算成新坐标，方向正确。
3. `native/include/radaer/player_view.hpp`：视角增量合并到 `motion`，不改坐标 `timestampMs`，同样是必要的统计语义。
4. `native/webui/radar/model.js`：`getRows()` 以 `now - p.timestampMs > HOLD_MS`（5,000 ms）调用 `forget()`，把位置没变化直接变成删除人物。`ingest()` 又只接受 2 秒内的坐标，导致删掉后即使 API 继续返回同一旧位置，也无法恢复显示，必须等下一次真正的位置字段。
5. 刷新页面/首次打开时，没有前端缓存，超过 2 秒的现存位置也不能进入缓存。这是另一个相同设计造成的显示缺口。

需要区分三个时间：**最近坐标变化、最近人物更新、最近战斗流通信**。坐标时间用于精度、速度预测和真实 Hz；不能单独用于判断人物是否仍存在。

## 原版处理与修复方向

原版 `reverse/protocol_trace/state_track.dis.txt` 的说明和 `slot_staleness()` 明确指出：静默时间是信息字段，静止人物也可能长时间不发送位置，不能单独作为离场判断。原版 `LiveView.snapshot` 的兜底 `STALE_HIDE_SEC` 是 **300 秒**，而不是 5 秒；还结合角色关闭、死亡、槽位复用等状态。

原版 `LiveView._handle_char_close` 区分关闭原因。当前 C++ 的 `CloseGuard` 仍在任意 close 时删除 actor 元数据，没有将原因和人物生命周期完整传给 `BattleTracker`/WebUI；所以不能只把 `HOLD_MS` 改成无限大，否则会留下已离场人物。

完整修复应接通人物生命周期：有效位置长期保存为「最后已知位置」，坐标陈旧时降低显示可信度并停止预测；用明确销毁/离场、槽位复用、换局和战斗流结束驱动清理，休眠/暂时缺坐标分别处理。保留独立的通信断线时限，避免接口故障时把缓存当成实时数据；不伪造新坐标时间、不抬高真实坐标 Hz。
